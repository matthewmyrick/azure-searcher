# Release Process

This document describes the automated release process for Azure Searcher.

## Overview

Azure Searcher uses an automated release process triggered by pull request labels. The process creates GitHub releases and builds cross-platform binaries using GoReleaser.

## Release Workflow

### 1. Pull Request Labels

When creating a pull request, add one of these labels to indicate the type of release:

- `major` - Breaking changes (e.g., 1.0.0 → 2.0.0)
- `minor` - New features, backwards compatible (e.g., 1.0.0 → 1.1.0)
- `patch` - Bug fixes, backwards compatible (e.g., 1.0.0 → 1.0.1)

### 2. Automated Process

When a labeled PR is merged to `main`:

1. **Auto Release Workflow** (`auto-release.yml`)
   - Detects the PR label
   - Calculates the new version number
   - Runs tests
   - Creates and pushes a git tag
   - Generates changelog from commit messages
   - Creates a GitHub release

2. **Release Workflow** (`release.yml`)
   - Triggered by the new tag
   - Runs tests again
   - Uses GoReleaser to build binaries for multiple platforms
   - Attaches binaries to the GitHub release

### 3. Supported Platforms

GoReleaser builds binaries for:

- **Linux**: amd64, arm64
- **macOS**: amd64, arm64 (universal binary)
- **Windows**: amd64

## Manual Release Process

If you need to create a release manually:

1. **Create and push a tag:**
   ```bash
   git tag -a v1.2.3 -m "Release v1.2.3"
   git push origin v1.2.3
   ```

2. **The release workflow will automatically:**
   - Build binaries
   - Create GitHub release
   - Upload artifacts

## Version Numbering

We follow [Semantic Versioning](https://semver.org/):

- **MAJOR**: Incompatible API changes
- **MINOR**: Backwards-compatible functionality additions
- **PATCH**: Backwards-compatible bug fixes

## Changelog Generation

Changelogs are automatically generated from commit messages between releases. To improve changelog quality:

- Use conventional commit messages:
  - `feat:` for new features
  - `fix:` for bug fixes
  - `docs:` for documentation changes
  - `refactor:` for code refactoring

## Release Artifacts

Each release includes:

- **Source code** (automatically generated by GitHub)
- **Binary archives** for each supported platform
- **Checksums** file for verifying downloads
- **Changelog** with commit history

## Installation Methods

Users can install releases via:

1. **Go install** (recommended):
   ```bash
   go install github.com/matthewmyrick/azure-searcher@latest
   ```

2. **Direct download** from GitHub releases:
   - Download the appropriate binary for your platform
   - Extract and place in your PATH

## GoReleaser Configuration

The release process is configured in `.goreleaser.yml`:

- **Cross-compilation** for multiple platforms
- **Archive formats**: tar.gz (Unix), zip (Windows)
- **Checksums** for security verification
- **Changelog filtering** to exclude noise

## Troubleshooting Releases

### Common Issues

**"Git is in a dirty state"**
- This happens when there are uncommitted changes
- Ensure the repository is clean before tagging

**"No configuration file found"**
- GoReleaser needs `.goreleaser.yml` in the repository root
- This file is already present in the project

**Release workflow fails**
- Check that tests pass locally
- Verify GitHub token permissions
- Review workflow logs for specific errors

### Manual Intervention

If automatic release fails:

1. **Check workflow logs** in GitHub Actions
2. **Fix the issue** (usually in .goreleaser.yml or workflows)
3. **Delete the problematic tag** if needed:
   ```bash
   git tag -d v1.2.3
   git push origin :refs/tags/v1.2.3
   ```
4. **Recreate the tag** after fixing

## Security Considerations

- **GitHub tokens** are automatically provided by GitHub Actions
- **Checksums** are generated for all artifacts
- **Signed releases** can be added in the future if needed
